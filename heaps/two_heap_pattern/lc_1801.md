# Backlog Orders — Max Heap and Min Heap

## Problem Approach

We are given a list of orders, where each order contains:

`[price, amount, orderType]`

- `price`: Price per unit.
- `amount`: Number of units in the order.
- `orderType = 0`: Buy order.
- `orderType = 1`: Sell order.

The goal is to process all orders in sequence, match buy and sell orders whenever their prices are compatible, and return the total number of units remaining in the backlog.

## Data Structures

We use two priority queues:

- **Max Heap (`maxHeap`)**: Stores pending buy orders as `{price, amount}`. The highest buy price is at the top.
- **Min Heap (`minHeap`)**: Stores pending sell orders as `{price, amount}`. The lowest sell price is at the top.

Each heap entry represents an entire order, rather than storing each unit separately. This is important because an order can contain a very large quantity.

## Algorithm

### 1. Processing a Buy Order

For a buy order, we try to match it with the cheapest pending sell order.

A match is possible when:

`buyPrice >= sellPrice`

While the new buy order has remaining quantity and a compatible sell order exists:

1. Retrieve the cheapest sell order's price and quantity.
2. Remove that order from the min heap.
3. Compare the quantities and match as many units as possible.
4. Preserve any unmatched quantity by reinserting the partially filled order.

After matching, if the buy order still has some quantity remaining, insert it into the max heap.

### 2. Handling Sell Quantity Greater Than Buy Quantity

Suppose the existing sell order has 10 units and the new buy order needs 4 units.

| Order | Price | Quantity |
|---|---:|---:|
| Existing sell | 7 | 10 |
| New buy | 10 | 4 |

We match 4 units.

- Buy order remaining: `4 - 4 = 0`
- Sell order remaining: `10 - 4 = 6`

The new buy order is completely fulfilled, so it is discarded. The existing sell order is reinserted into the min heap with 6 units remaining.

### 3. Handling Buy Quantity Greater Than Sell Quantity

Suppose the existing sell order has 4 units and the new buy order needs 10 units.

| Order | Price | Quantity |
|---|---:|---:|
| Existing sell | 7 | 4 |
| New buy | 10 | 10 |

We match all 4 available sell units.

- Buy order remaining: `10 - 4 = 6`
- Sell order remaining: `4 - 4 = 0`

The existing sell order is completely fulfilled and discarded. The matching loop continues in case another compatible sell order exists.

If no more compatible sell orders remain, the unmatched 6 units of the buy order are inserted into the max heap.

### 4. Processing a Sell Order

For a sell order, we use the opposite logic: match it against the highest-priced pending buy order.

A match is possible when:

`sellPrice <= buyPrice`

We repeatedly match quantities, remove fully fulfilled orders, and reinsert partially fulfilled orders with their remaining quantities.

If the sell order still has an unmatched quantity after processing, we insert it into the min heap.

## Why Do We Use `min(amount, quantity)`?

The matched quantity is the smaller of the two remaining quantities:

`matched = min(amount, quantity)`

This ensures that we never match more units than either order contains.

In the implementation, the two cases are handled using comparisons:

- If `amount >= quantity`, the existing order is completely fulfilled, so we subtract its quantity from `amount` and discard it.
- Otherwise, the new order is completely fulfilled. We subtract `amount` from the existing order's quantity, reinsert that order, and set `amount = 0`.

This correctly handles both complete and partial order fulfillment.

## Why Do We Use Modulo `1,000,000,007`?

The problem requires the final backlog quantity modulo:

`MOD = 1,000,000,007`

The backlog can contain a very large number of units, so calculating the unrestricted total can exceed the range of a 32-bit integer.

We calculate the total as:

`total = (total + remainingQuantity) % MOD`

for every remaining order.

We use `long long` for `total` to make the addition safe before applying the modulo. Taking the modulo during accumulation also keeps the running total bounded.

The final answer is returned as an integer because the modulo result is within the `int` range.

**Important:** We apply the modulo only when calculating the final backlog total. We must not apply it to order quantities during matching because that would change the actual quantities and produce incorrect results.

## Complexity Analysis

Let `n` be the number of orders.

- **Time Complexity:** `O(n log n)` — each order is inserted into or removed from a priority queue at most a constant number of times per matching operation, with each heap operation taking `O(log n)` time.
- **Space Complexity:** `O(n)` — in the worst case, all orders remain unmatched in the two heaps.

## Key Takeaways

- Use a max heap for buy orders and a min heap for sell orders.
- Store `{price, amount}` instead of storing individual units.
- Match as many units as possible without exceeding either order's quantity.
- Discard fully fulfilled orders and preserve partially fulfilled orders.
- Add an order to its own heap only if it has unmatched quantity remaining.
- Use modulo `1,000,000,007` when accumulating the final backlog total, not during matching.
